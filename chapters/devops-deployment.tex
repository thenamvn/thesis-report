\section{DevOps and Deployment Strategy}
\label{sec:devops-strategy}

The transition from a monolithic development environment to a distributed microservice architecture necessitates a robust DevOps strategy. As defined by \citet{kim2016}, DevOps is not merely a set of tools but a culture and practice that aims to shorten the systems development life cycle while delivering features, fixes, and updates frequently in close alignment with business objectives. For the TEKUTOKO platform, a container-centric deployment strategy orchestrated by Kubernetes (K8s) was selected to ensure high availability, scalability, and maintainability \citep{burns2019}. This section details the architectural decisions and implementation specifics of the deployment pipeline.

\subsection{Containerization with Docker}
\label{subsec:containerization}

To achieve environment consistency across development, testing, and production, the platform utilizes Operating-system-level virtualization, commonly known as containerization \citep{merkel2014}.

\subsubsection{Rationale for Containerization}
Unlike traditional Virtual Machines (VMs) which emulate hardware and require a full guest operating system, containers share the host system's kernel while isolating processes in user space. This results in significantly lower overhead, faster startup times, and greater portability detailed in Table \ref{tab:vm-vs-container}.

\begin{table}[htbp]
\centering
\caption{Comparison of Virtual Infrastructure Approaches}
\label{tab:vm-vs-container}
\begin{tabular}{p{4cm} p{5cm} p{5cm}}
\toprule
\textbf{Feature} & \textbf{Virtual Machines} & \textbf{Docker Containers} \\
\midrule
\textbf{Isolation} & Hardware-level (Hypervisor) & OS-level (Namespaces/Cgroups) \\
\textbf{Size} & Large (GBs) & Small (MBs) \\
\textbf{Startup Time} & Minutes & Milliseconds/Seconds \\
\textbf{Dependencies} & Manually managed per VM & Encapsulated in Image \\
\bottomrule
\end{tabular}
\end{table}

\subsubsection{Implementation Details}
Crucially for this project, containerization solves the "dependency hell" problem inherent in the Python document processing microservice. This service requires specific versions of system-level binaries—\texttt{pandoc} for LaTeX conversion and \texttt{imagemagick} for media processing—which are difficult to manage consistently across different developer machines (Windows/macOS) and production servers (Linux).

A custom \texttt{Dockerfile} was engineered for the Python service to encapsulate these dependencies:

\begin{lstlisting}[language=bash, caption={Snippet of Python Microservice Dockerfile}, label={lst:dockerfile}]
# Use python:3.9-slim for reduced image size
FROM python:3.9-slim

# Install system-level dependencies for document processing
RUN apt-get update && apt-get install -y \
    pandoc \
    imagemagick \
    && rm -rf /var/lib/apt/lists/*

# Relax ImageMagick security policy to allow PDF/DOCX processing
RUN sed -i 's/rights="none" pattern="PDF"/rights="read|write" pattern="PDF"/' \
    /etc/ImageMagick-6/policy.xml

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
\end{lstlisting}

\subsection{Orchestration with Kubernetes}
\label{subsec:kubernetes}

While Docker manages individual containers, a production microservice system requires a higher-level orchestrator to manage lifecycle, networking, and scaling. Kubernetes (K8s) was selected over simpler solutions like Docker Compose for its robust capabilities in state management and self-healing.

\subsubsection{Cluster Architecture and Topology}
The Kubernetes cluster is designed following a modular topology where services are exposed through a unified Ingress Controller. The architecture ensures that internal services (Database, Python Microservice) are not directly exposed to the public internet, reducing the attack surface.

\subsubsection{Resource Organization and Manifests}
The deployment configuration follows the Infrastructure as Code (IaC) paradigm, stored in a structured \texttt{k8s/} directory within the project repository. This structure separates configuration concerns:

\begin{lstlisting}[language=bash, caption={Kubernetes Manifest Directory Structure}]
k8s/
|-- 00-config/        # ConfigMaps and Secrets (Credentials)
|-- 01-database/      # MySQL StatefulSet and PVCs
|-- 02-python-app/    # Document Processing Microservice
|-- 03-node-app/      # Main API Backend
|-- 04-frontend/      # React Client Application
`-- 05-ingress/       # Ingress Routing Rules
\end{lstlisting}

\subsubsection{Service Discovery and Networking}
A critical challenge in microservice architecture is service discovery—how the Node.js backend locates the Python microservice without hardcoded IP addresses (which change dynamically in K8s).

To solve this, Kubernetes \textbf{Services} are employed. A Service defines a logical set of Pods and a policy by which to access them.
\begin{enumerate}
    \item \textbf{Internal DNS:} The core backend connects to the database via the hostname \texttt{mysql-service} and to the docx-processor via \texttt{python-backend-service}. Kubernetes' internal DNS resolver automatically routes these hostnames to the correct ClusterIP.
    \item \textbf{Ingress Routing:} An Nginx Ingress Controller handles Layer 7 (HTTP) routing, directing external traffic based on URL paths:
    \begin{itemize}
        \item \texttt{/api/*} $\rightarrow$ Node.js Backend (Port 3000)
        \item \texttt{/python-api/*} $\rightarrow$ Python Service (Port 8000)
        \item \texttt{/*} $\rightarrow$ Frontend Service (Port 80)
    \end{itemize}
\end{enumerate}

\subsubsection{State Management and Persistence}
Although the application logic is stateless \citep{newman2021}, data persistence is critical. **PersistentVolumeClaims (PVCs)** constitute the mechanism used to abstract storage provisioning:
\begin{itemize}
    \item \textbf{Database Persistence:} A 5Gi PVC attached to the MySQL Deployment ensures user data is preserved even if the database container crashes or restarts.
    \item \textbf{Processing Workspace:} The Python microservice mounts a 2Gi PVC at \texttt{/app/outputs}. This shared workspace simplifies the processing pipeline, allowing the service to extract heavy media files from DOCX archives to disk without consuming the container's ephemeral memory, preventing \textit{Out Of Memory (OOM)} errors during high load.
\end{itemize}

\subsection{Continuous Deployment Pipeline}
\label{subsec:cicd}

A GitOps-based workflow automates the deployment process. The CI/CD pipeline, visualized in Figure \ref{fig:cicd-pipeline}, ensures a seamless transition from code commit to production deployment.

\begin{figure}[htbp]
\centering
\includegraphics[width=1.0\textwidth]{figures/cicd-pipeline.png}
\caption{Automated CI/CD Pipeline Workflow}
\label{fig:cicd-pipeline}
\end{figure}

Upon a commit to the \texttt{main} branch:
\begin{enumerate}
    \item \textbf{CI Phase:} GitHub Actions runners execute unit tests and linter checks to verify code integrity.
    \item \textbf{Build Phase:} Docker images are built for each service, tagged with the commit SHA (e.g., \texttt{docx-processor:a1b2c3d}), and pushed to the container registry.
    \item \textbf{CD Phase:} The pipeline authenticates with the Kubernetes cluster and updates the Deployment images:
    \begin{verbatim}
    kubectl set image deployment/docx-processor-deploy \
        docx-processor=registry/docx-processor:a1b2c3d
    \end{verbatim}
    \item \textbf{Rolling Update:} Kubernetes performs a rolling update, incrementally replacing old Pods with new ones, ensuring zero downtime for users.
\end{enumerate}
